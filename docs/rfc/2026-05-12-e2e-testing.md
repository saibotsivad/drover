# Goal

Add a full end-to-end test suite for the Drover stack that a developer can run locally with a single command, and that can also run automatically (or manually) in GitHub Actions.

# Summary

Introduce an `e2e/` directory containing a single entry-point shell script (`run.sh`) with subcommands that manage the full lifecycle of a local Drover stack built from source, plus a numbered suite of bash test scripts that assert correctness at the API and log level. A new GitHub Actions workflow runs the suite on demand (and eventually on every PR).

# Proposed E2E Testing Strategy

## Core Principle: Separate Lifecycle Stages

The key insight is that a developer needs a **tight inner loop**: change code → rebuild one container → run tests. This argues for explicit lifecycle separation rather than one monolithic script.

**Single entry point**: `e2e/run.sh <command>`

```
./e2e/run.sh up         # Build from source, start full stack, wait for health
./e2e/run.sh down       # Tear down and clean up volumes
./e2e/run.sh restart    # Rebuild + restart all containers (full reinstall cycle)
./e2e/run.sh restart orchestrator  # Rebuild + restart just one service (tightest loop)
./e2e/run.sh test       # Run assertions against an already-running stack
./e2e/run.sh ci         # up + test + down (one-shot, for GitHub Actions)
```

A developer's day looks like: `./e2e/run.sh up` once, then `./e2e/run.sh restart orchestrator && ./e2e/run.sh test` in a tight loop.

## Directory Structure

```
e2e/
├── run.sh                   # Main entry point (subcommands above)
├── docker-compose.e2e.yml   # Stack definition with deterministic ports/keys for testing
├── lib/
│   ├── assert.sh            # pass/fail helpers, exit-on-first-failure vs collect-all
│   ├── api.sh               # curl wrappers: wait_healthy(), create_container(), exec_cmd()
│   └── logs.sh              # jq helpers: assert_no_errors(), assert_log_contains()
├── tests/
│   ├── 01-health.sh         # All three services respond to health checks
│   ├── 02-images.sh         # Orchestrator can discover the builder image
│   ├── 03-privileged-container.sh  # Full lifecycle: create → running → exec (echo $VAR) → stop
│   └── 04-standard-container.sh   # Same but with gVisor — skipped if runsc not present
└── logs/                    # Auto-created during test runs, gitignored
```

The tests are sourced and run by `run.sh test` in order. Each one either passes or exits non-zero, which stops the suite. Logs from all three Docker containers are captured to `e2e/logs/` throughout.

## The Key Test (03-privileged-container.sh)

1. POST `/containers` with the builder image + env var `DROVER_TEST_VAR=hello_drover`
2. Poll GET `/containers/{id}` until status = `running` (or timeout)
3. POST `/containers/{id}/exec` with command `echo $DROVER_TEST_VAR`
4. Poll for result; assert exit code 0 and stdout contains `hello_drover`
5. POST `/containers/{id}/stop`
6. Assert final status = `stopped`
7. Parse `e2e/logs/orchestrator.log` with jq; assert zero lines with `level == "ERROR"`

This exercises the full socket protocol, state machine, and log output in one pass.

---

## API Key

The test API key is hard-coded: `DROVER_API_KEY` (the SHA-256 hashed value) is committed in `docker-compose.e2e.yml`, and the corresponding unhashed `API_KEY` is committed in a test env file sourced by the test scripts. This avoids any key-generation step before running tests.

## gVisor Strategy

The core privileged-container test (test 03) **doesn't need gVisor** — privileged containers bypass it. So the base test suite runs on any machine with Docker.

For test 04 (standard containers under gVisor), the proposal is:
- In **GitHub Actions**: install gVisor as a setup step in the CI workflow. It's supported on Ubuntu runners, takes ~60 seconds, and gives full-fidelity testing. No toggle needed.
- On **developer laptops**: if `runsc` is not detected, test 04 prints `SKIP: gVisor not installed` and exits 0. Developer can install gVisor to enable it.
- **No `DROVER_REQUIRE_GVISOR` toggle added to the orchestrator** — at least not yet. If CI can handle it, there's no reason to add complexity to the production code.

### Required: `--host-uds=all` runtime flag

After `runsc install`, the `runsc` runtime entry in `/etc/docker/daemon.json` must include `--host-uds=all` in its `runtimeArgs`. Without this flag, gVisor blocks the guest agent from connecting to the orchestrator socket that is bind-mounted into the container, and every non-privileged container will time out in `initializing` and fail with `init_timeout`.

The flag is safe in context: it permits Unix socket connections only to paths accessible through the container's own mount namespace, which for a non-privileged Drover container is exactly the one per-container orchestrator socket. The Docker socket is not bind-mounted into non-privileged containers, so it remains unreachable.

```json
"runtimes": {
  "runsc": {
    "path": "/usr/local/bin/runsc",
    "runtimeArgs": ["--host-uds=all"]
  }
}
```

This applies equally to developer laptops and CI runners.

## Log Strategy

### The Core Problem: Async Boundaries

Drover's operations are async. When you `POST /containers`, the HTTP response returns immediately with `status: initializing`, but the real work — socket creation, `docker run`, the guest agent connecting and sending `ready` — happens in background tasks over the next several seconds. The logs relevant to a given API call are generated *after* the response arrives. This means log capture must span from before the HTTP request through to when the background work reaches a terminal state. The wait/polling loop is inside the log capture window, not after it.

### Timing Model

Each logical test step records two timestamps:

- **T1**: Captured *before* the HTTP request is sent, to catch any pre-flight orchestrator activity
- **T2**: Captured *after* the terminal state is confirmed via polling, plus a ~500ms grace buffer before pulling logs — some log lines emit after the DB write that changes state

Then `docker logs drover-orchestrator --since T1 --until T2` gives the exact window for that step.

### Log Chunk Files

Each logical step produces one chunk file. The file is structured plain text with labeled sections — readable by both humans and automated systems without preprocessing.

```
STEP:      create-container
TEST:      03-privileged-container
RUN_ID:    2026-05-12T14:30:00.000Z
STARTED:   2026-05-12T14:30:01.234Z
COMPLETED: 2026-05-12T14:30:05.923Z
RESULT:    PASS

--- REQUEST ---
POST http://localhost:8000/containers
{"image": "drover-builder", "privileged": true, "env": {"DROVER_TEST_VAR": "hello_drover"}}

--- RESPONSE ---
HTTP 201
{"id": "abc123def", "status": "initializing", ...}

--- WAIT ---
target_status: running
timeout: 30s
elapsed: 4689ms
polls: 4
final_status: running

--- ORCHESTRATOR LOGS ---
{"ts":"2026-05-12T14:30:01.412Z","level":"INFO","logger":"orchestrator.app","msg":"POST /containers 201"}
{"ts":"2026-05-12T14:30:01.830Z","level":"INFO","logger":"orchestrator.container_manager","msg":"creating socket"}
...

--- WEBAPP LOGS ---
(none in window)

--- FAILURE ---
(none)
```

For exec steps specifically, the exec output (stdout/stderr, exit code) travels over the Unix socket and is returned via the API — it does not appear in orchestrator logs. Both sources are included as separate sections, since they cannot be accurately interleaved by time:

```
--- EXEC RESULT ---
exit_code: 0
stdout: hello_drover
stderr: (none)

--- ORCHESTRATOR LOGS ---
{"ts":"...","level":"INFO","msg":"received output message from socket","container_id":"abc123def"}
{"ts":"...","level":"INFO","msg":"received result message from socket","exit_code":0}
...
```

### File Structure

```
e2e/logs/
└── 2026-05-12T14:30:00Z/               # RUN_ID: timestamp of run.sh test invocation
    ├── summary.log                     # Pass/fail per step, total elapsed, first failure pointer
    ├── 01-health/
    │   └── 01-webapp-health.log
    ├── 02-images/
    │   └── 01-list-images.log
    └── 03-privileged-container/
        ├── 01-create-container.log     # POST → wait for running
        ├── 02-exec-command.log         # POST exec → wait for result → assert stdout
        └── 03-stop-container.log       # POST stop → wait for stopped
```

`summary.log` is the entry point for automated systems — it identifies which step failed first and names the chunk file to inspect. Each chunk file is fully self-contained for diagnosis.

### Library Design

In `lib/logs.sh`, two functions bracket each step:

```bash
step_begin "create-container"
# ... API call + polling ...
step_end   # records T2, pulls logs from T1→T2+buffer, writes chunk file
```

A bash `ERR` trap (enabled with `set -E`) ensures that even unexpected failures — `curl` returning no output, `jq` choking on malformed JSON — write a partial chunk file before exiting, rather than leaving `logs/` in an ambiguous state. The partial chunk includes whatever was captured up to the point of failure, plus the failure reason in the `FAILURE` section.

On GitHub Actions, the entire `logs/` directory is uploaded as an artifact on failure.

## GitHub Actions

New workflow: `.github/workflows/e2e.yml`
- **Trigger**: `workflow_dispatch` (manual) to start. Can be promoted to automatic on PRs targeting `main` once the suite is stable and fast enough.
- Steps: checkout → (install gVisor) → `./e2e/run.sh ci` → upload `e2e/logs/` artifact on failure

### Proof of Concept

Before building the full suite, a PoC workflow was used to validate all the technically risky steps in GitHub Actions: building both images from source, starting the orchestrator with the correct Docker socket and socket-directory bind-mounts, launching a privileged container and confirming the guest-agent handshake, exec-ing a command and asserting the output, building a new image from inside the privileged container via the host Docker daemon, stopping a container, and finally launching and exec-ing a non-privileged container under gVisor (including discovering the `--host-uds=all` requirement above).

See `.github/workflows/e2e-poc.yml` for the complete validated sequence. Total wall-clock time on a fresh `ubuntu-latest` runner is approximately 3–4 minutes.
